# Phase 8 Stage 4-5 Multi-Role Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a bounded manifest/instance projection for Planner, Implementer, and Reviewer roles and connect it to the existing Commander ownership and dependency contracts without adding a scheduler or new authority.

**Architecture:** `RoleManifest` is immutable data describing a role's bounded responsibility and references existing Task/Resource/Budget policies instead of duplicating them. `RoleInstance` points at an existing Process Coordination peer and reuses `PeerRecord.is_live()` for lease freshness. A thin `MultiRolePlanAdapter` validates role/task assignments and delegates plan persistence and execution to the existing Commander/Supervisor boundaries; it owns no queue, retry, budget, approval, or integration state.

**Tech Stack:** Python 3.10+, stdlib dataclasses/enums/JSON, existing `Task`, `TaskIntelligencePolicy`, `PeerRecord`, Commander plan validator/store, pytest, architecture check, compileall.

**Spec:** `docs/V2_DETAILED_ROADMAP.md` Stage 4 (`4-A`–`4-E`) and Stage 5 (`5-A`–`5-E`), plus `docs/CODEX_WORK_COORDINATION.md`.

## Global Constraints

- Preserve Stage 1 `NOT_READY`, D9 proposal-only, Human/Host Authority, existing Task UUID/dependency/ownership/lease, UNKNOWN/reconciliation, and protected paths.
- Do not add a second Task scheduler, StateStore, Budget system, Retry framework, Agent framework, Provider router, or integration authority.
- Role manifests contain policy references and bounded ceilings; they never issue authority or choose a concrete model/provider.
- Role instances reuse existing Process Coordination peer identity and strict lease freshness; expired peers cannot be treated as current.
- Worker-eligible pure contracts, serializers, fixtures, and focused tests default to the qualified Free Worker; Codex retains architecture, security, authority, recovery, lifecycle, review, and integration.
- Do not call live Provider, Compression, MCP wire, OS registration, external Codex session, paid Provider, or D9 real mutation for this deterministic foundation slice.
- Never persist credentials, raw Provider responses, raw conversations, or full sensitive payloads.
- Every production behavior change has a focused test written and observed failing before implementation; run focused tests, architecture, and compileall before a slice commit.

- `RoleManifest.from_dict()` / `.to_dict()` validates bounded role data, task types, capabilities, risk/privacy ceilings, action lists, references, and finite concurrency.
